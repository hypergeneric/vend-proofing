# Developing Vend

Vend is a PHP application with a customer storefront and a separate JavaScript administration interface. Preserve its established UI and behavior while modernizing the runtime and security boundaries. The [audit](VEND-PRODUCT-DISCOVERY-AND-TECHNICAL-AUDIT.md) maps the architecture; the [storage strategy](VEND-STORAGE-STRATEGY.md) records the superseded document-store proposal; the [modernization log](VEND-MODERNIZATION.md) records current phase decisions and results.

## Local runtime

The main Lando app is configured in `.lando.yml`. Run `lando start`, then use the HTTPS URLs reported by `lando info`. Application data lives under `vend-proofing-data/`; keep existing data and credentials out of commits. The Lando `lamp` recipe includes a database service, but Vend uses its own SQLite database for administrators, PHP sessions, galleries, media metadata, pricing, discounts, customer proofing, carts, orders, payments, fulfillment records, contacts, and message logs. The Lando MySQL service is incidental. `Records` owns ordinary relational lists; `Proofing` owns customer selections; `OrderRecords` owns purchase snapshots. The main `Gateway` switch handles set-list, image, and media actions. Physical media files remain on disk.

`MediaFiles` handles physical uploads, sideloads, snapshots, and file deletion. `Gateway` routes the admin request and `Records` owns its SQLite metadata. `Configuration` stores compact JSON settings in SQLite and reads source defaults from `vend-proofing-core/defaults/`; empty `_value` and `_attributes` fields are supplied when the admin loads a document; `Flatfile` and `SimpleXML4` have been removed. The public admin layout lives beside the settings defaults in `vend-proofing-core/defaults/admin.json`. Lando loads `.lando/php.ini` for development diagnostics. PHP errors go to the ignored `vend-proofing-data/storage/php-debug.log`; they are not printed in HTTP responses. Follow the file locally with `tail -f vend-proofing-data/storage/php-debug.log`. The storage `.htaccess` blocks HTTP access to the log. A new or cleared local installation needs a writable `vend-proofing-data/storage/` directory before PHP can create the log.

For an isolated PHP 8.4 smoke check, run `bash scripts/phase1-smoke.sh`. It creates synthetic records and a synthetic admin account under `/tmp`, runs the cached PHP 8.4 container without network access, and removes the fixture afterward. It tests login, session, Gateway access, CLI reset, and logout as well as the older storefront checks. It also runs Node syntax checks on the static storefront/admin bundles and inline page configuration, so Node must be available on the host. Run `npm run build` before the smoke scripts after changing asset sources. Run `bash scripts/basic-set-smoke.sh` for a fresh-install upload-set test with no flat-file page/image records; it also checks relational proofing, cart, offline checkout, invoice, pricing, and Dropbox image metadata. For a disposable interactive site, run `bash scripts/phase1-dev.sh` and open `http://127.0.0.1:8048/`; it starts with an empty page catalog, disables PHP mail and network client functions, and prints its synthetic admin login. Create an Upload Set and upload a JPEG in admin to test the SQLite path. The PHP development server uses `scripts/dev-router.php` to keep private data inaccessible. Neither script uses the live data directory.

### Administrator account

For a fresh installation, run `lando php scripts/install.php`, then create the first administrator with `lando php scripts/admin-account.php create USERNAME EMAIL`. Apply later schema migrations with `lando php scripts/migrate.php`. Reset a forgotten password with `lando php scripts/admin-account.php reset USERNAME`. Both account commands prompt for a password of at least 12 characters; terminal echo is disabled when possible. The unified database lives at `vend-proofing-data/auth/vend.sqlite` and holds the account, administrator sessions, PHP order-session state, saved JSON configuration, and an installation secret for gallery access. Back up the database with application data. The web server must deny HTTP requests into `auth/`; the current Lando Apache setup does this through `vend-proofing-data/.htaccess`. The former `admin.sqlite`, PHP session files, and saved `storage/*.xml` documents are not read by the new runtime. The JSON cutover is a fresh-install change. The active Lando data tree was cleared and schema 012 installed with `json_text`; it has no administrator account yet. Create one with `lando php scripts/admin-account.php create USERNAME EMAIL`, then QA the settings editors. The former development data is temporarily preserved at `/tmp/vend-pre-json.SfPfOG`; no XML settings were imported. Do not run `scripts/migrate.php` expecting it to convert XML rows.

This step supports one full administrator. The customer email proofing session is separate. The admin SPA still posts to the Gateway with a `token` field, now a session-bound request token. Keep it on new admin actions, including uploads and auxiliary forms. Do not add a browser-accessible setup path or send passwords by email.

The retired `get_xml`, `get_files`, and `get_set` Gateway actions have no application callers. Admin XML controls use `setup_load` and `setup_defaults`; admin tables use the typed `set_list` and media `*_list` actions. The storefront reads its tax rules directly while rendering the gallery.

Limited-use discounts are claimed by `prequalify_order` before payment. A retry with the same order ID and quote keeps the claim; abandoned checkouts keep it counted. A completed order converts the claim to a redemption. The photographer can extend the code limit in admin when needed. See the [modernization log](VEND-MODERNIZATION.md) for the payment qualification still open.

Checkout Gateway failures send stable keys such as `discount_expired` and `invalid_order`. Storefront copy for these keys belongs in `defaults/language.json` and is read through `L10N`; PHP exception prose must not become customer-facing text.

For Phase 2A, `scripts/phase2a-stage-demo.py SOURCE_DATA NEW_FIXTURE_DIRECTORY` made a sanitized local copy of the historical demo. It refuses to overwrite an existing fixture. It excludes customer orders and sessions, removes service credentials, and disables mail, payment, and cron settings. Media and public gallery metadata were copied unchanged; keep both the source and fixture private. The local Lando `vend-proofing-data/storage/` and `uploads/` currently hold this staged copy. `scripts/phase2a-demo-smoke.sh` captured the pre-cutover storefront, admin, upload-gallery, ZIP-gallery, and category-gallery baseline. Its gallery checks are historical reference checks; ZIP galleries are retired in the new release.

The current local Lando demo data is disposable reference data. Its old page table is no longer read by the relational catalog, so the current set list is empty until new sets are created. Use the isolated fresh-install smoke or development site for the new catalog acceptance test. Historical deployment compatibility is not a requirement; preserve current behavior and identifiers where they help the product, not to accommodate old PHP installations.

Run `bash scripts/phase2a-upload-smoke.sh` for a disposable PHP 8.4 test of category-set multipart uploads, folder categories, relational records, storefront rendering, restart persistence, and image resizing. It verifies that category and image table files are absent and ignored if planted. It uses synthetic JPEG media and Docker with no external network access; it does not alter the Lando data.

## CSS development

Use Node 22 or newer on the host. From the repository root:

```sh
npm ci
lando start
npm run dev
```

Open the local HTTPS URL printed by BrowserSync. It proxies `https://vend-proofing.lndo.site`, starts at port 3000, and selects a free port if that port is occupied. Edit `src/scss/`; saving rebuilds the CSS and replaces the stylesheets without resetting the page. JavaScript source changes rebuild the scripts and reload the page; HTML template changes also reload the page. The proxy listens on loopback and disables mirrored clicks/forms. Override the target or initial port when needed: `VEND_PROXY=https://another-local-site VEND_DEV_PORT=3010 npm run dev`. Stop it with Ctrl-C.

`npm run build:css` compiles styles once; `npm run build` rebuilds both CSS and JavaScript. `npm run watch:css` watches and compiles without starting a proxy. `npm run check:css` checks that the committed output matches its sources. `npm run test:css` also checks the five bundle outputs, stylesheet links, local font/image references, and synthetic theme settings in the network-disabled PHP 8.4 Docker image used by the other smoke scripts; it never loads application data.

| Source | Purpose | Static output |
|---|---|---|
| `src/scss/storefront.scss`, `storefront/` | Base styles, forms/dialogs, navigation, browser, cart, checkout, clickwrap, packages, splash, contact | `vend-proofing-core/css/storefront.css` |
| `src/scss/admin.scss`, `admin/` | Administration navigation, dialogs, tables, panels, forms, statistics | `vend-proofing-core/css/admin.css` |
| `src/scss/admin-shell.scss`, `admin-shell/` | Administration contact/setup screen | `vend-proofing-core/css/admin-shell.css` |
| `src/scss/invoice.scss`, `invoice-print.scss` | Invoice screen and print styles | `vend-proofing-core/css/invoice.css`, `invoice-print.css` |

Edit the SCSS sources, then commit the generated CSS and source maps alongside them. Deployment serves these files directly and does not require Node. Source maps point browser developer tools back to the SCSS files. Entry-point `@use` order preserves the existing cascade. Dependency order lives in `assets.config.js`: each CSS entry has a `source` SCSS file and optional `prepend` and `append` arrays of CSS files. The build concatenates those lists around the compiled SCSS without changing the cascade. For example, the storefront appends its jQuery UI styles. Admin prepends its controls, then appends jQuery UI and Bootstrap. Both SCSS entry points load `shared/reset` before their component modules, keeping the reset in its original cascade position. Both entry points use the shared reset and jQuery UI 1.12.1 package. The storefront-only invalid-input background belongs in its SCSS, not the reset. Vendor CSS sources live under `src/vendor/`; the shared reset lives at `src/scss/shared/_reset.scss`. Edit those arrays to add stylesheets. The running watcher reloads configuration and build helpers, and rebuilds when CSS, SCSS, the config, or a build-helper script changes. Restart `npm run dev` after editing the Gulpfile itself. Supplied dependency rules and license comments are preserved; PostCSS rebases image/font URLs and combines source maps.

Pages link only the five compiled stylesheets; `2.styles-admin.tmpl` is removed. Shared application and vendor images live under `vend-proofing-core/graphics/`; administration badge/loader images live in its `admin/` subdirectory, and Bootstrap fonts under `vend-proofing-core/fonts/bootstrap/`. CSS sources no longer live under `admin/` or JavaScript library directories. The shared `src/vendor/jquery-ui/` package uses the fuller original administrator component build; its common rules match the former storefront package. Both use `vend-proofing-core/graphics/jquery-ui/`. The unused historical standalone `video` template still references its external Video.js runtime and styles, outside these application entry points.

The former `?/css/...` endpoints and `tmpl/css/` templates are retired. `tmpl/html/2.theme.tmpl` emits a small inline `:root` property block for PHP configuration values: colors, font family and scaled sizes, spacing, logo dimensions, print-image visibility, and sprite URLs. It also emits existing custom-font `@font-face` declarations. SCSS uses `var(--vend-...)`; PHP syntax does not belong in SCSS or the build output. Keep a complete `url(...)` in URL-valued properties rather than putting `var(...)` inside a quoted URL. Stylesheet links use the build file's modification time for cache invalidation. CSS custom-property support is required.

## JavaScript development

Run `npm run dev` for the shared BrowserSync workflow. Saving JavaScript under `src/` rebuilds the scripts and reloads the page. `npm run build:js` builds scripts once; `npm run watch:js` watches them without starting a proxy. `npm run check:js` checks committed output against its sources. `npm run test:js` checks bundle syntax, source-map targets, page links, duplicate inclusion, and synthetic PHP runtime configuration. It needs the same network-disabled PHP 8.4 Docker image as the CSS smoke. The broader foundation smoke also checks rendered page configuration and retired asset routes.

| Source | Purpose | Static output |
|---|---|---|
| `src/js/admin/` | Administrator bootstrap, helpers, components, dialogs, applications, panels | `vend-proofing-core/js/admin.js` |
| `src/js/storefront/vend/`, `src/js/storefront/bootstrap.js`, `src/js/storefront/l10n.js`, `src/js/storefront/tracking.js`, and configured dependencies | Storefront application and dependencies | `vend-proofing-core/js/storefront.js` |
| `src/vendor/jquery/jquery.js` | Shared jQuery prepended to both bundles and copied unchanged for invoice pages | `vend-proofing-core/js/jquery.js` |

`assets.config.js` has a `js` section with ordered `prepend`, `source`, and `append` arrays. Add a new file to the appropriate list. Identical jQuery and Modernizr copies are shared under `src/vendor/jquery/` and `src/vendor/modernizr/`, and both bundles refer to these vendor sources. Shared Base64, browser-detection, hashchange, MD5, and Spin.js cores also live under `src/vendor/`. Admin additionally loads `src/vendor/spin/jquery.spin.js`; storefront does not use that adapter. Bootstrap retains only the used `src/vendor/bootstrap/bootstrap.min.js` and `src/vendor/bootstrap/bootstrap.min.css` sources; its Glyphicons font files remain under `vend-proofing-core/fonts/bootstrap/`; toggle scripts and styles share `src/vendor/jquery-toggles/`. All third-party scripts now live under `src/vendor/`; application `extend/` folders are removed. The two jQuery UI component builds live together as `jquery-ui.admin.min.js` and `jquery-ui.storefront.min.js` in `src/vendor/jquery-ui/`. Vendor CSS is colocated with its matching package. The custom `.progress()` helper lives in `src/js/storefront/vend/helpers/Progress.js`, separately from the scroll-containment plugin, and keeps its prior execution order. The jPlayer file names now match their upstream headers; core still loads before playlist. A `copy` section copies the shared jQuery source unchanged for invoice pages, without a third application bundle or separate source map. These lists preserve the former PHP load order explicitly; each admin panel is included once. Bundling concatenates plain browser scripts with separators and source maps. It preserves existing globals, closures, names, and vendor versions, without introducing modules or transpilation. New syntax errors fail the build before any JS output is replaced. Commit the generated JavaScript and source maps with source changes. The old `vend.js` and `vend-core.js` generated files are removed; `vend-proofing-core/admin/` no longer contains application sources.

PHP emits `window.VEND_CONFIG` before the static script tag, like a localized WordPress script object. `tmpl/html/2.config-storefront.tmpl` supplies the namespace, base URL, URI labels, image-resampling/watermark settings, and processed public language strings. `tmpl/html/2.config-admin.tmpl` supplies the namespace and public admin layout. JSON encoding escapes characters that could close a script tag. Static bootstrap files map the object to the existing application globals, and `classes.helpers.L10N.get()` reads its language table. Keep per-request PHP values in these HTML configuration templates, not in build sources. Existing gallery/order startup markup remains rendered in HTML. Asset links use modification times for cache invalidation.

The former `?/js/global/`, `?/js/admin/`, and `?/js/vend/` assembly routes return HTTP 404, as do the retired CSS routes. PHP no longer concatenates scripts or writes bundles into the source tree during requests.

## Development rules

- Keep changes small and test the contract of the affected subsystem.
- Edit JavaScript in `src/js/admin/` or `src/js/storefront/`, then run `npm run build:js` or use `npm run dev`. Edit styles in `src/scss/`. Do not hand-edit the generated files under `vend-proofing-core/js/` or `vend-proofing-core/css/`; see the asset-development sections above.
- Match the tab-indented PHP style in touched files. Use named intermediate values and readable method bodies for new persistence code; keep SQL and multi-step writes easy to follow.
- Preserve gallery SUIDs, public URL structure, row formats, visual design, and low-friction email proofing unless a specific defect requires change.
- Do not treat order totals, payment status, or delivery eligibility supplied by a browser as authoritative.
- Do not run mail, payment, Dropbox, or destructive migration operations against live data during tests.
- Update [VEND-MODERNIZATION.md](VEND-MODERNIZATION.md) with decisions, tests, limitations, and the next step when a phase changes.
- Keep user-facing instructions in the [manual](MANUAL.md); agent workflow belongs in [AGENTS.md](../AGENTS.md).

## Payment development

Run `bash scripts/payment-smoke.sh` for synthetic, network-disabled PHP 8.4 payment tests. It exercises trusted prices, shipping/taxes, discount policy without case sensitivity, packages/downloads, offline/free orders, provider fixtures/signatures, duplicate and out-of-order callbacks, retries, eight concurrent submissions/events, refunds, receipt failures and entitlement. It never requires merchant credentials or makes a charge. The basic-set smoke now uses configured catalog prices for its order fixtures rather than arbitrary browser quotes.

`CheckoutQuote` verifies the existing browser calculator against assigned catalog records and configuration. `OrderRecords` freezes accepted selections/rules/amounts before a provider call and retains its existing first 25 projected fields. Search rows append payment status, safe error code and refunded amount for admin. `Payments` owns provider attempts, event deduplication and fulfillment/notification claims; `StripePayment` and `PayPalPayment` independently verify remote state before reconciliation. `PaymentGateway` handles only the new checkout/provider actions before the existing Gateway dispatch. New admin payment actions still require `Auth` and its request token.

Migration 013 extends existing tables; no separate commerce database or queue service is introduced. Internal monetary snapshots retain Vend's hundredth-unit contract and adapters explicitly convert provider currency units. Provider calls and email sends stay outside SQLite write transactions. Failed/expired attempts retain their references when a safe replacement is created. An ambiguous creation older than the provider's conservative idempotency window requires review, rather than risking a duplicate charge. Only server-confirmed paid/free orders receive digital entitlement. Existing email-based invoice access remains, while direct processing requires the matching authorized order session and SQLite entitlement.

Use the new asset workflow above for payment UI edits. Sandbox/live credentials, webhook subscriptions, receipt recovery, pricing limits and external qualification procedures belong in the [manual](MANUAL.md#payment-setup). Do not put credentials in source, fixtures, generated JavaScript or diagnostic logs. Account-specific sandbox operations remain a separate verification step from mocks.

## Current sequence

Phase 1 established a PHP 8.4 smoke runtime and focused first-party fixes. Phase 2A established a representative real-world baseline using demo data. Phase 2B introduced single-admin authentication and a first public Gateway/media access boundary; the remaining direct routes and commerce actions still need review. The persistence foundation installs one SQLite schema. All application table records and saved JSON settings now use it, including customer proofing selections and orders; ZIP galleries are retired. Source JSON defaults, physical media, and disposable derivatives remain files. Payment providers and server-side pricing validation require their own qualification before release. The modernization log is the source of truth for progress within each phase.
